### Observed Behavior

Statische Assets sind hash-versioniert (`app.js?v=…`, `styles.css?v=…`) — gute
Cache-Invalidierung. **Aber** die grösste Ressource `data/index.json` wird mit
`cache: "no-store"` geladen (`app.js`, `status.js`), d.h. jeder Besuch — auch der
wiederkehrende — lädt die ~324 KB komplett neu. Für ein täglich genutztes
Dashboard verpufft damit der Cache-Vorteil beim wichtigsten Asset.

### Expected Behavior

Wiederkehrende Besucher laden nicht alles neu; das grösste Asset revalidiert
(304) statt vollständigem Re-Download; Text-Ressourcen komprimiert.

### Evidence

- File: `site/assets/app.js:70` — `fetch(path, { cache: "no-store" })`
- File: `site/assets/status.js:155` — `fetch(path, { cache: "no-store" })`
- Messung lokal: Zweit-Fetch überträgt erneut volle 324 KB (kein 304)

### Risk Description

Betrieblich gering (Datei ändert sich nur bei Deploys), aber jeder Reload kostet
volle 324 KB statt einer schlanken 304-Revalidierung.

### Remediation

- `no-store` → `no-cache` (revalidieren mit ETag; Pages liefert ETags) für den
  Katalog-Fetch. Freshness bleibt, Bandbreite sinkt beim Zweitbesuch.

### Effort Estimate

**S** — ein Wort pro Fetch.

### Dependencies / Blockers

Verwandt mit PERF-004 (Doppel-Fetch). Zusammen umsetzen.

### Verification After Fix / Vorbehalt

- **Unbestätigt (Umgebungslimit):** `Cache-Control`- und `Content-Encoding`-Header
  wurden über einen lokalen `http.server`-Spiegel geprüft, nicht über die echte
  Pages-Auslieferung — der lokale Server setzt weder Langzeit-Cache noch Brotli.
  Manuelle Prüfung auf der Live-URL: DevTools → Network → Response-Headers von
  `styles.css` (`Cache-Control`, `Content-Encoding: br/gzip`) und Zweitbesuch auf
  304/`memory cache` gegenprüfen.
- Re-Run PERF-005: Katalog-Fetch liefert beim Zweitbesuch 304 statt 200 (voll).
- Commit-Referenz: `perf: no-cache statt no-store für den Katalog-Fetch [PERF-005]`
