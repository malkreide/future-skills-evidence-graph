### Observed Behavior

Das grösste Asset ist `data/index.json` (~324 KB). Auf `index.html` wird es
**mehrfach** geladen, jeweils mit `cache: "no-store"`:

- `app.js` → `loadData()` (Katalog rendern)
- `status.js` → `loadGenerated()` (nur das Feld `generated_at` lesen)

Beide Fetches nutzen `no-store`, deduplizieren also nicht. Im Netzwerk-Panel der
Begehung erscheint `index.json` zweimal mit je 324 KB.

Messung (`audit/evidence/2026-07-18-browser-walk.json`):

```
index.cwv.transferKB: 716
index.cwv.biggest: [ index.json 324, index.json 324, app.js 42, styles.css 20, status.js 7 ]
```

Positiv: Keine Bilder, keine Webfonts (Inter fällt auf System-Stack zurück),
JS/CSS klein, Assets hash-versioniert. Das Seitenbudget wird fast vollständig von
der doppelt geladenen JSON bestimmt.

### Expected Behavior

Das grösste Asset wird nur einmal übertragen; Startseite < 1.5 MB (erfüllt), aber
ohne unnötige Doppel-Downloads.

### Evidence

- File: `site/assets/app.js:69-90` — `fetchJson(path)` mit `{ cache: "no-store" }`, `loadData()`
- File: `site/assets/status.js:152-165` — `loadGenerated()` fetcht denselben `index.json` erneut mit `cache: "no-store"`
- Messung: `index.cwv.biggest` (index.json 324 KB × 2)

### Risk Description

Nutzer im Zug / mit Prepaid-Volumen / auf altem Gerät zahlen ~324 KB doppelt.
`status.js` braucht aus der 324-KB-Datei nur ein einziges Datum (`generated_at`).

### Remediation

- `status.js` nicht die volle `index.json` erneut laden lassen, sondern das
  `generated_at`-Feld aus einer bereits geladenen Quelle beziehen (z.B. `app.js`
  legt das Datum global/als `data-`Attribut ab, oder ein winziges separates
  `meta.json` mit nur `generated_at`).
- Für den Katalog-Fetch `cache: "no-store"` überdenken: Pages liefert mit ETag
  aus; `no-cache` (revalidieren) statt `no-store` (nie cachen) erlaubt 304-Antworten.

### Effort Estimate

**S–M** — kleine Umstrukturierung des generated_at-Bezugs.
