### Observed Behavior

Die In-App-Fehler- und Leerzustände sind durchweg gut:

- Skill-Liste ohne Treffer: «Keine Treffer — Filter reduzieren oder Suchbegriff anpassen.»
- LP21-Tabelle leer: «Keine Lehrplan-21-Mappings für diesen Filter.»
- Daten-Ladefehler: «Daten konnten nicht geladen werden» + Meldung (`app.js:1144`)
- Pipeline-Panel: nutzerfreundliche Meldungen inkl. Rate-Limit-Hinweis, keine rohen Statuscodes (`status.js:177-188`)

**Aber:** Es gibt keine eigene `404.html`. Eine falsche URL unter dem Pages-Pfad
landet auf der generischen GitHub-Pages-404-Seite ohne Weg zurück ins Dashboard.

### Expected Behavior

Eigene 404-Seite im Site-Stil mit Navigation zurück zum Dashboard (USE-009,
Pass-Kriterium «Eigene 404-/Fehlerseite mit Navigation zurück»).

### Evidence

- Kein `site/404.html` im Repo; `build_site.py` kopiert keine 404-Seite nach `public/`
- Positiv-Gegenprobe (In-App-Fehler): `site/assets/app.js:1143-1145`, `site/assets/status.js:177-188`

### Risk Description

Ein toter Link (geteilte veraltete URL, Tippfehler) führt Nutzer auf eine
fremde, englische GitHub-404-Seite — sie wirken aus dem Produkt geworfen und
finden ohne manuelles URL-Kürzen nicht zurück.

### Remediation

Kleine `site/404.html` im Site-Stil anlegen (Topbar + Hinweis + Link auf
`index.html`) und in `build_site.py` mit nach `public/` kopieren. GitHub Pages
serviert `404.html` automatisch bei unbekannten Pfaden.

### Effort Estimate

**S** — eine statische Seite + eine Kopierzeile im Build.

### Dependencies / Blockers

Keine.
